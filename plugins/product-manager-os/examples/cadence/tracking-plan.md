# Tracking Plan — AI Blocker Detector

**Owner:** Priya Raman (PM) · **Implementer:** Tom Aliyev (eng) · **Tool:** Amplitude
**Status:** approved · **Verify by:** 2026-07-03 (48h after rollout to 10%)

**TL;DR**
- 6 events, 1 deprecation. Everything traces to a question in the table below; nothing was added "just in case."
- The one we almost missed: `blocker_dismissed`. Without it we can measure detection but not whether teams think detection is *right* — which is the actual question.
- `team_id` is required on every event. Every question Cadence asks is eventually "by team."

## Questions this plan must answer
| # | Question | Answered by |
|---|---|---|
| 1 | What share of teams with the detector on see at least one blocker surfaced in week 1? | `blocker_detected` + `team_id` |
| 2 | Do surfaced blockers get acted on, or ignored? | `blocker_acknowledged` vs `blocker_dismissed` |
| 3 | Does the detector improve week-2 team survival (our #1 priority)? | `check_in_posted` cohorted on detector exposure |
| 4 | Are we surfacing too many? Where does dismissal rate cross into noise? | `blocker_dismissed` / `blocker_detected` by `detection_confidence` |
| 5 | Do managers open the digest more when it contains a blocker? | `digest_opened` + `contained_blocker` |
| 6 | Which detection source is worth keeping? | `blocker_detected` + `source` |

## Naming convention
`object_action`, past tense, snake_case. Properties snake_case. Enum values lowercase.
Examples: `blocker_detected` · `blocker_dismissed` · `digest_opened`

## Events

### `blocker_detected`
- **Fires when:** the detector writes a blocker record to the digest — not when the model returns a candidate. Candidates that fall below threshold never reach a human and must not count.
- **Fires once per:** blocker record
- **Owner:** Tom · **Answers:** Q1, Q4, Q6

| Property | Type | Required | Allowed values | Notes |
|---|---|---|---|---|
| `team_id` | string | yes | — | join key |
| `source` | enum | yes | `check_in_text`, `missed_checkin`, `sentiment` | which detector fired |
| `detection_confidence` | enum | yes | `high`, `medium`, `low` | bucketed, not a float — floats become unqueryable |
| `days_since_signup` | integer | yes | — | the property we'd otherwise wish we had |

### `blocker_acknowledged`
- **Fires when:** a manager clicks through to the underlying check-in from the digest.
- **Owner:** Tom · **Answers:** Q2

### `blocker_dismissed`
- **Fires when:** a manager explicitly marks a blocker as not real. **Does not fire** on scroll-past — silence is not dismissal and conflating them would inflate our accuracy read.
- **Owner:** Tom · **Answers:** Q2, Q4

### `digest_opened`
- **Fires when:** the digest email or in-app view renders for a manager.
- New property this release: `contained_blocker` (boolean) — **Answers:** Q5

## Identity & joins
- **User identifier:** `user_id`, stable across web and Slack.
- **Account identifier:** `team_id` — required on every event, no exceptions.
- **Known gap:** Slack-originated check-ins carry a Slack user id that maps to `user_id` on a nightly job. Same-day Slack analysis is unreliable; stated here so nobody discovers it mid-analysis.

## Explicitly NOT tracked
- Blocker text content — privacy. We track that one existed, its source and confidence, never what it said.
- Model latency — belongs in engineering observability, not product analytics. No product question needs it.
- Hover and scroll on the digest — no question requires it, and it would triple event volume.
